# Main v2.17 Codex Integration Design

## 目标

将 `main` 中从共同基点 `c0d08b1` 到 `5d7d80d` 的 119 个上游提交完整纳入
`codex` 历史，同时保持 `codex` 分支现有的 Codex App 操作模型，不退回 Claude Code
专用的命令、目录和配置方式。

完成后的 skill 继续命名为 `icodex`，用户入口继续是 `$icodex <command>`。上游新增的
`help`、`run`（对应上游全流程 `start`）、`fast`、`log`、`patch`、`doc`、`limit`、
`readme`、`status`、`list` 和 `install` 能力也通过同一入口使用。

## 已确认约束

- 保留 `codex` 的 full mode：Diagnose → Plan → Implement → Self Review → Audit → Verify。
- 保留七阶段 staged mode：init → plan → review → merge → code → deepcheck → audit。
- 为避免破坏已有调用，`$icodex start` 继续作为 `$icodex plan` 的别名并在 plan 后暂停；
  上游自动串联步骤 1～6 的能力改由 `$icodex run <requirement>` 提供。
- 保留 `$icodex-review` 作为独立异模型终审 skill，`icodex` 本身不冒充异模型审查。
- 保留 `agents/openai.yaml` 和 `references/domain-checklists.md`。
- 新运行统一写入 `.ai/icode/{timestamp}-{short-task}/`。
- 全局知识库、索引和约束统一写入 `~/.codex/icode_data/`。
- 旧 `.icode_output/` 与 `~/.claude/icode_data/` 只读兼容，不向其中写入新状态。
- 不修改 `~/.claude.json` 或其他 Claude 配置。
- `/icode ...` 只作为迁移说明中的旧写法，不作为 Codex 主入口。
- 不引入与上游无关的重构或新依赖。

## 方案选择

采用“真实 Git 合并 + 语义适配层”，而不是 squash、复制文件或直接选择一侧冲突版本。

真实合并保证上游 119 个提交进入 `codex` 的祖先历史，未来可以继续通过 merge-base 判断
同步点。冲突处理以 `codex` 的运行契约为外层，以 `main` v2.17 的规则和新增能力为内层：

1. 无冲突新增文件完整接收。
2. `SKILL.md` 保留 Codex frontmatter、模式选择和产物策略，再导入上游命令路由、约束、
   MCP 覆盖、决策锚点和历史检索规则。
3. `steps/00_init.md` 到 `steps/06_audit.md` 以上游版本为内容基线，统一替换为 Codex
   调用、路径和工具语义，再恢复 staged mode 的暂停规则。
4. 新增步骤文件保留上游行为，但入口改为 `$icodex`，状态和目录落到 Codex 路径。
5. Claude 专用安装与全局存储逻辑必须经过适配；无法在 Codex 中等价执行的操作明确降级，
   不伪装成已经完成。

不采用“全部选择 ours”，因为会遗漏上游 v2.17 的核心能力；不采用“全部选择 theirs”，
因为会破坏 `$icodex`、`.ai/icode`、同模型自审和 `$icodex-review` 分工。

## 组件设计

### 1. 顶层路由与运行契约

`SKILL.md` 是唯一顶层运行契约，负责：

- 识别 full mode 与 staged mode。
- 将 `$icodex start|plan|review|merge|code|deepcheck|audit` 路由到单阶段核心步骤。
- 将 `$icodex run` 按 `steps/run.md` 路由到 staged full 自动串联流程；`run` 在阻断问题
  出现时仍须暂停。
- 将 `$icodex help|fast|log|patch|doc|limit|readme|status|list|install` 路由到辅助步骤；
  `help` 的真源为 `steps/help.md`。
- 定义新写入目录、旧数据只读兼容、状态词表和恢复规则。
- 声明 Codex 工具可用性检查及降级原则。
- 保留同模型自审、Principal Engineer 审计和外部终审边界。

步骤文件不得重新定义与顶层冲突的命令、根目录或外部审查职责。

### 2. 工单与状态数据

项目内新工单目录：

```text
.ai/icode/{timestamp}-{short-task}/
```

其中保存 `.ico_metadata.json`、工作流产物、review/deepcheck 记录以及 patch/readme 产物。
辅助命令是否创建工单，沿用上游 v2.17 的语义：`help`、`doc`、`limit`、`status` 查询、
`list` 和 `install` 不创建项目工单，也不写 metadata 或全局索引；`init`、`log` 和新的
full/staged 流程按规则创建或复用。

所有持久化运行，不论 full mode 还是 staged mode，都必须创建 `.ico_metadata.json`，并包含：

- `artifact_layout`：`"concise"` 或 `"staged"`。
- `workflow_kind`：`"codex_full"`、`"staged_full"` 或 `"staged_fast"`。
- `artifact_map`：逻辑产物名到当前目录相对路径的映射。
- `status`：staged mode 沿用上游状态词表；Codex full mode 使用 `full_in_progress` 或
  `completed`，当前阶段写入 `current_phase`。
- `completed_steps`：仅 staged mode 使用；full mode 写空数组。
- `completed_phases`：full mode 使用 `diagnose|plan|implement|self_review|audit|verify`；
  staged mode 写空数组。
- 上游共享字段：`ticket_id`、`requirement`、`code_files`、`created_at`、`patch_count`、
  `patch_history`、`verdict` 及历史检索所需字段。

状态机不变量：full mode 的 `completed_phases` 必须是
`[diagnose, plan, implement, self_review, audit, verify]` 的无重复前缀，`current_phase` 只能是
下一未完成阶段；完整序列出现时 `status` 必须为 `completed`，否则必须为
`full_in_progress`；完成时 `current_phase=null`。staged mode 的 `completed_steps` 允许以
可选且互斥的 `"0"` 或 `"log"` 开头，之后必须是 `["1","2","3","4","5","6"]`
的无重复前缀；`status` 必须与最后
一个完成步骤及当前 in-progress 步骤匹配。任何乱序、重复、跳号或状态不匹配都拒绝写回，
`status --validate` 同样报告为错误。

`artifact_map` 使用以下稳定键。表中路径表示该产物成功发布后的值；运行创建时所有键都
初始化为 `null`，每个产物先写同目录临时文件、校验后原子重命名，再通过临时 metadata
文件加原子替换发布路径。若 metadata 更新失败，路径保持 `null`；重试时只有在现存文件
通过当前步骤校验后才能复用并补写映射，禁止辅助命令猜文件名：

| 稳定键 | concise 布局 | staged 布局 |
|---|---|---|
| `requirement` | `null`，需求真源为 metadata `requirement` | `00_init.md`，未经过 init 时可为 `null` |
| `root_cause` | `RCA.md` | `log_analysis.md`，非 log 工单可为 `null` |
| `plan` | `PLAN.md` | `01_plan.md` |
| `plan_review` | `null` | `02_review.md` |
| `final_plan` | `PLAN.md` | `03_plan_final.md` |
| `implementation` | `IMPLEMENT.md` | `04_code_review_fix.md` |
| `deepcheck` | `SELF_REVIEW.md` | `05_deepcheck.md` |
| `audit` | `AUDIT.md` | `06_audit.md` |
| `patches` | `08_patch.md` | `08_patch.md` |
| `delivery_report` | 运行时生成的交付报告相对路径 | 运行时生成的交付报告相对路径 |
| `delivery_brief` | 运行时生成的跨领域简报相对路径 | 运行时生成的跨领域简报相对路径 |

`status`、`patch`、`readme` 和历史检索必须先读取 `artifact_map`。例如，full mode 的
`readme` 从 `RCA.md`、`PLAN.md`、`AUDIT.md` 取材，而不是要求不存在的编号文件。
`patches` 仅在第一次 patch 成功后设置；交付报告两键仅在对应文件成功发布后设置。

`status --validate` 根据状态和布局使用以下必需键，除此之外的键允许为 `null`：

- concise：`completed_phases` 每包含一个已完成阶段，就依次要求 `diagnose→root_cause`、
  `plan→plan`、`implement→implementation`、`self_review→deepcheck`、`audit→audit`；
  `verify` 要求前述全部键且 `status=completed`。
- staged：`init_in_progress` 要求 `requirement`；`log_done` 要求 `requirement+root_cause`；
  `plan_done` 要求 `plan`；`review_in_progress` 只要求 `plan`，`review_done` 追加要求
  `plan_review`；`plan_finalized` 追加要求 `final_plan`；`code_in_progress` 要求
  `final_plan`，`code_done` 追加要求 `implementation` 和非空 `code_files`；
  `deepcheck_in_progress` 要求 `implementation`，`deepcheck_done` 追加要求 `deepcheck`；
  `completed` 要求 `plan+final_plan+implementation+deepcheck+audit`，只有 metadata 表示
  经过 init/log/review 时才分别追加要求 `requirement/root_cause/plan_review`。
- 两种布局均仅在 `patch_count>0` 时要求 `patches`；仅在 metadata 记录已生成交付报告时
  要求 `delivery_report+delivery_brief`。

不得用 staged 的固定 7 文件清单判定 concise 布局损坏，也不得因尚未到达未来阶段而要求
未来产物。

读取与旧工单迁移顺序：

1. 优先读取 `.ai/icode/` 下的当前格式。
2. 用户明确恢复旧任务时，允许读取 `.icode_output/`。
3. 旧任务继续前执行可恢复的两阶段迁移，而不是跨两个目录续写。项目工单目录与 Codex
   全局索引无法组成单一文件系统事务，因此禁止宣称整体原子；迁移 ID 固定为
   `sha256(realpath(legacy_source)+legacy_ticket_id)[:16]`，最终目录固定为
   `.ai/icode/legacy-{safe_legacy_ticket_id}-{migration_id}`，其中 `safe_legacy_ticket_id` 只
   保留 `[A-Za-z0-9._-]`、其他字符替换为 `_`。迁移目标项目根来自旧索引条目的
   `project_path`；用户直接指定本地旧工单时，则由 `<project_root>/.icode_output/` 的父子
   关系反推出项目根。迁移前必须确认项目根和 `legacy_source` 均为真实目录、目录本身不是
   符号链接，且 `legacy_source` 的 realpath 位于该项目根的 `.icode_output/` 下并包含可解析
   的 `.ico_metadata.json`；任一条件不满足或目标项目不可写时立即停止。最终目录创建在该
   legacy 项目的 `.ai/icode/` 下，固定目标确保跨工程迁移和所有重试命中同一目录：
   - 目标目录已存在且 `migration_id` 不同或 metadata 不可解析时停止并报告冲突；
     `migration_state=completed` 时直接复用，`migration_state=prepared` 时跳过复制、从索引
     发布步骤恢复。
   - 在 `.ai/icode/.migrate-{ticket_id}-{nonce}/` 创建临时目录，递归复制旧工单目录内的
     普通文件并保留相对路径；遇到符号链接、设备文件或其他特殊文件立即失败，禁止移动、
     硬链接或符号链接。
   - 将 metadata 转成 `artifact_layout="staged"`，生成仅包含已存在产物的 `artifact_map`，
     并写入 `legacy_source`、`legacy_ticket_id`、`migration_id`、`migration_at`、
     `migration_schema` 和 `migration_state="prepared"`。
   - 转换 metadata 前后分别生成普通文件的 SHA-256 清单；除 `.ico_metadata.json` 外，
     相对路径和哈希必须完全一致。随后校验 metadata 可解析、`artifact_map` 指向的非空
     文件存在；把源目录完整清单哈希写入 `legacy_manifest_sha256`。失败时保留旧目录不变并
     删除临时目录。
   - 校验通过后把临时目录原子重命名为固定最终目录；发布后失败不得删除最终目录。
   - 只把当前迁移工单导入 `~/.codex/icode_data/index.json`。索引必须在同目录临时文件中
     完整写入并校验，再原子替换。若 `ticket_id` 已指向同一 `migration_id`，幂等复用；若
     指向不同来源，生成 `{legacy_ticket_id}-migrated-{migration_id[:8]}`，同时保留
     `legacy_ticket_id`。
   - 索引发布成功后，通过原子 metadata 替换把 `migration_state` 改为 `completed`。
     若目录已发布但索引或最终标记失败，下次运行读取固定目录中的 `prepared` 状态，从索引
     步骤继续；禁止重新复制或创建第二个目录。
   - 复用 `prepared` 或 `completed` 目标前重新计算源清单哈希；若与
     `legacy_manifest_sha256` 不同，停止并报告“旧源在迁移后发生变化”，不得静默复用、覆盖
     已迁移工单或自动生成第三份副本。
4. 迁移后所有 `status --verdict`、patch、索引更新和后续步骤只修改新工单及 Codex 索引；
   旧 `.icode_output/` 与 Claude 索引始终保持只读。

### 3. 全局数据

Codex 全局根目录：

```text
~/.codex/icode_data/
```

其下保留上游的数据模型：项目/模块知识库、历史索引、约束和相关元数据。所有读取使用
Codex + Claude 的只读合并视图，而不是按根目录整体回退：

- 工单索引同时解析两侧 `index.json`，按 `ticket_id` 合并；同 ID 且同来源时 Codex 条目
  优先，同 ID 但来源不同时给 Claude 条目分配只读展示 ID `legacy:{ticket_id}:{path_hash}`，
  用户尝试修改该条目时先走工单迁移。
- `project_docs`、`module_docs` 和 `limits` 按各自的 project/module/limit key 合并；同 key
  读取 Codex 版本，Codex 缺少的 key 或文件才从 Claude 补齐。
- 搜索缓存键使用两侧数据源清单的 SHA-256：清单包含两个 `index.json` 以及参与候选检索的
  project/module/limit 文件相对路径和内容哈希；任一已有文件内容变化、增删或来源切换都会
  改变缓存键。禁止仅依赖目录 mtime，因为原地修改已有文件不会可靠更新目录 mtime。
- 合并视图不自动批量复制旧数据。任何创建、续期、stale、verdict 或文档更新只写 Codex
  数据；需要修改旧工单时先执行上面的可恢复迁移。

对于尚未迁移但检索命中的 legacy-only 工单，纯查询不产生写入；需要更新 `hit_count`、
`last_used_at`、`stale` 或 `stale_reason` 时，在 Codex 索引创建/更新
`legacy_overlay=true` 的覆盖条目，只保存 `legacy_source`、原 `ticket_id`、来源哈希和这些
可变检索字段，不把它标记成已迁移工单。overlay 在 Codex 索引中的 `ticket_id` 使用只读
展示 ID `legacy:{legacy_ticket_id}:{migration_id[:8]}`，原 ID 单独保存在
`legacy_ticket_id`，从而不破坏索引唯一性。合并读取时 overlay 的可变字段覆盖对应 Claude
原记录，其他字段仍来自 Claude。verdict、patch 或任何工单内容修改不得只写 overlay，
必须先迁移；迁移完成后删除 overlay 并以正常 Codex 工单条目替换。

所有 read-modify-write 使用仓库内提供的跨平台锁助手：全局索引写入持有
`~/.codex/icode_data/.index.lock`，单工单 metadata/产物映射写入持有运行目录的
`.ico.lock`；锁等待上限 10 秒，超时停止并报告持有者信息，不自动破锁。一次操作同时需要
两把锁时固定先取 index lock、再取 run lock，释放顺序相反，禁止改变顺序。持锁期间重新读取
最新内容、写同目录临时文件、校验后原子替换；测试覆盖并发 overlay/索引更新不丢记录、
同工单并发 patch 不重复编号以及锁超时无部分写入。同一 legacy 迁移另用目标项目
`.ai/icode/.migration-locks/{migration_id}.lock` 串行化复制和目录发布；迁移两阶段不同时持有
migration lock 与 index lock，目录发布后释放 migration lock，再独立获取 index lock 更新
索引，最后独立获取 run lock 标记完成，依靠 `migration_state` 实现跨阶段恢复。

### 4. MCP 与工具适配

`install` 和 MCP 文档以 Codex 配置方式为准。本机 Codex CLI 的配置真源为
`~/.codex/config.toml`，MCP 通过 `codex mcp add|list|get|remove` 管理；实现不得直接拼接
TOML。具体契约：

- 不写 `~/.claude.json`。
- 不假定 Claude Code 的工具名或斜杠命令存在。
- `$icodex install --dry-run [name]` 只输出环境缺口和将执行的 `codex mcp add` 操作。
- 用户显式调用 `$icodex install [name]` 后，才允许安装依赖并调用
  `codex mcp add <name> -- <command...>`；执行前遵循 Codex 的权限确认流程。
- 新增 `mcp/install-codex.sh` 作为 Codex 唯一安装入口；原 `mcp/install.sh` 及写
  `~/.claude.json` 的注册脚本保留为 legacy，不得由 `$icodex install` 调用。
- `install-codex.sh` 通过 `ICODEX_CODEX_BIN` 注入 CLI 路径，未设置时默认调用 `codex`；
  测试必须注入临时 fake CLI，禁止改写 `HOME`、`CODEX_HOME` 或真实 Codex 配置。
- 任何依赖下载或环境修改前，先构造候选配置并运行 `codex mcp list --json` 做冲突检查。
  比较时对象键排序、命令路径规范化为绝对路径，数组保持顺序，忽略纯展示字段；已存在且
  规范化配置相同则幂等跳过。若同名配置不同，输出现有配置与候选配置的结构化差异并返回
  退出码 2，且不得下载依赖、调用 remove 或改写配置；用户必须自行处理冲突后重试，
  `$icodex install` 不提供破坏性 `--force` 路径。
- 批量安装单项失败时继续检查其余项，最终只要存在失败项就返回非零并列出失败原因。
- Codex 卸载使用 `mcp/uninstall-codex.sh [name]`：默认只展示目标配置并要求交互确认，
  `--dry-run` 永不修改，非交互环境未传 `--yes` 时拒绝执行；确认后才调用
  `codex mcp remove`，不触碰 Claude 注册项或用户密钥文件。
- 运行时先检查当前 Codex 会话可用工具。
- 缺少可选 MCP 时使用步骤文件声明的本地或普通工具降级路径。
- 缺少强制能力且无法可靠降级时停止对应子步骤，并报告缺少的能力和未验证风险。
- 保留上游 MCP 源码和测试；任何依赖下载和注册都只能由用户显式 `install` 调用触发，
  普通 `$icodex` 工作流不得自动安装或启用 MCP。

## 合并冲突规则

- `README.en.md`：接受上游删除，将有效 Codex 英文内容迁入 `README.md`。
- `README.md`：基于上游 v2.17 功能清单重写为 Codex 版本。
- `SKILL.md`：人工组合，禁止整体采用 ours 或 theirs。
- `steps/00_init.md` 至 `steps/06_audit.md`：基于上游内容，逐项恢复 Codex 契约。
- `steps/03_merge.md`：即使 Git 自动合并，也要做语义检查。
- 新增文件：先完整接收，再扫描 Claude 路径、命令和配置写入。

## 数据流

1. 用户调用 `$icodex <command>`。
2. `SKILL.md` 选择 Codex full、单阶段 staged、`run` 自动串联或辅助命令路径。
3. 路由器读取对应 `steps/*.md`，并解析当前 `.ai/icode` 工单状态。
4. 需要历史或项目知识时读取 Codex + Claude 按 key 合并的只读视图；所有写入仍只落到
   `~/.codex/icode_data`。
5. 步骤执行后只写 Codex 路径，并更新 `.ico_metadata.json` 或 Codex 全局索引。
6. 自审、审计和验证完成后报告结果；只有用户请求时才交给 `$icodex-review`。

## 错误与恢复

- 未找到可复用工单时，遵守上游命令的创建/报错规则，不猜测目录。
- 新旧 metadata 冲突时按可恢复的两阶段迁移规则生成或复用 Codex 工单；迁移完成前禁止
  推进步骤。
- `artifact_map` 缺少当前命令的必需键或目标文件不存在时，输出缺失键和布局类型并停止，
  不回退猜测上游固定文件名。
- MCP 不可用时区分强制能力与可选增强；不可验证的结论必须带残余风险。
- 安装步骤不得因为未识别 Codex 配置格式而回退写入 Claude 配置。
- 合并后的任何残留冲突标记、失效相对链接、两套主写入目录或两套主命令均视为阻断问题。

## 验证标准

### Git 完整性

- `git merge-base --is-ancestor main HEAD` 返回成功。
- 合并结果保留 `agents/openai.yaml` 与 `references/domain-checklists.md`。
- 工作树不存在未解决冲突。

### 契约扫描

- frontmatter 名称为 `icodex`。
- 主调用方式为 `$icodex`。
- `$icodex start` 仍等价于单阶段 `$icodex plan`；`$icodex run` 才自动串联步骤 1～6。
- `.ai/icode` 和 `~/.codex/icode_data` 是唯一新写入根目录。
- 主动 Codex 文件 `SKILL.md`、`steps/**`、`references/**`、`README*`、`scripts/**`、
  `templates/**`、`tools/**`、`mcp/install-codex.sh` 和 `mcp/uninstall-codex.sh` 中，
  `/icode`、`.icode_output`、`~/.claude` 只能出现在同一行明确标注
  `legacy/兼容/只读` 的迁移说明中。
- legacy 白名单仅包括 `mcp/install.sh`、`mcp/uninstall.sh`、`mcp/*/install.sh`、
  `mcp/*/uninstall.sh`、`mcp/*/scripts/register_mcp.py` 和 `mcp/*/README.md`；这些文件允许
  保留 Claude 路径，但任何主动 Codex 文件不得执行或链接其安装/卸载入口。
- 不存在写入 `~/.claude.json` 的 Codex 安装路径。

### 文档与引用

- 所有 `steps/`、`references/`、模板和脚本相对链接存在。
- README 中的命令、路径和版本与 `SKILL.md` 一致。
- 所有新增命令都有对应步骤文件和路由说明，包括 `steps/help.md` 与 `steps/run.md`。
- `$icodex help` 的命令清单与 `SKILL.md` 路由和 `steps/` 文件集合一致。

### 可执行检查

- 运行 `tests/test_schema_migration.sh`。
- 运行 `tools/lint_mcp_coverage.py`。
- 运行仓库内可用的 cheap-research 测试；若缺少依赖，记录精确缺失项。
- 对 shell 脚本执行语法检查，对 Python 文件执行编译检查。
- 添加并运行 full/concise 与 staged 两种 `artifact_map` 的 `status --validate`、patch、readme
  路由测试，证明辅助命令不依赖固定编号文件名；覆盖阶段乱序、重复、跳号及 status 不匹配
  均被拒绝。
- 添加并运行旧工单迁移测试：成功复制、重复迁移幂等、ticket_id 冲突改名、复制失败不改
  源目录、跨工程目标定位、路径逃逸拒绝、目录发布后索引失败可恢复、索引原子替换、迁移后
  verdict 只双写 Codex metadata/index、源清单变化时拒绝静默复用。
- 添加并运行 Codex/Claude 合并视图测试：两侧非冲突记录都可见、同 key 时 Codex 优先、
  同 ticket_id 不同来源可区分、overlay 不破坏 ticket_id 唯一性、任一侧文件内容变化都会
  改变缓存键。
- 添加并运行命令路由测试：`start` 单阶段暂停、`run` 串联、`help` 完整列出命令。
- 添加并运行 Codex MCP 安装 dry-run 与幂等测试；通过 `ICODEX_CODEX_BIN` 注入记录调用的
  临时 fake CLI，覆盖同名同配置跳过、同名异配置退出码 2 且不调用 remove；禁止改写
  `HOME`、`CODEX_HOME` 或开发机真实 `~/.codex/config.toml`。
- 添加并运行 MCP 副作用顺序与卸载安全测试：配置冲突发生在依赖下载之前，卸载 dry-run
  零写入，非交互无 `--yes` 拒绝执行。
- 添加并运行契约扫描测试，验证 legacy 白名单中的旧路径被允许、主动 Codex 文件中的旧
  写入口被阻断，且 `$icodex help` 不创建目录或修改 metadata/index。
- 添加并运行锁与并发测试：全局索引并发更新不丢记录、同工单并发 patch 序号唯一、统一
  锁顺序无死锁、同 migration_id 并发迁移只发布一个目标、10 秒超时后无目录/metadata/index
  部分写入。

## 非目标

- 不修改 `external-review` 分支。
- 普通工作流不自动安装或启用外部 MCP；只有用户显式调用 `$icodex install` 才进入安装流程。
- 不改写上游 MCP 服务的业务算法，除非 Codex 路径/注册适配确实需要。
- 未经验证不推送集成分支，也不覆盖远程 `codex`。
